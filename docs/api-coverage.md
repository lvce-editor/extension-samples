## Validation status

A clean static build using published server/shared-process 0.123.1 and editor-worker 19.73.4 passes the original status bar, output, rename, organize-imports, and preference read/update/cancel/reset scenarios. Cache cleanup, editor decorations, and local authentication cancellation/session removal/reload also pass.

The strengthened preference acceptance test additionally checks that the source IDE keeps its original font. It currently fails: setting the preview to 18px changes the source IDE from 15px to 18px. The renderer's `Application.execute` explicitly forwards `Preferences.get` and `Preferences.update` to the global command map. This is an unresolved isolation defect, so the preferences example is not ready to ship.

The new selection, closing-tag and signature-documentation acceptance cases expose prerequisite runtime defects with focused fixes awaiting full CI. Document-symbol breadcrumbs remain absent. Enabling them from a post-mount setup hook did not resolve that failure. These candidates remain unvalidated until their actual browser assertions pass on published dependencies. The final sample quality matrix and lifecycle acceptance are still required.

## Verified application-runtime restrictions

Inspected extension-management-worker source at merged prerequisite `7704caeb775f706f5822a1355137a648a4eec677` (published 4.90.2):

- `GetOrCreateIsolatedExtensionHostWorker.ts` creates an application-scoped callback for the playground's isolated extension. Its non-specialized calls route through `Extensions.invokeForApplication`.
- `CreateExtensionCommandMap.ts` deliberately forwards application callbacks to that router instead of using legacy secret callbacks.
- `CommandMap.ts`'s `invokeForApplication` only accepts state-wrapped commands, an explicit set of shared theme commands, and its switch cases. `Extensions.getSecret`, `Extensions.storeSecret`, and `Extensions.deleteSecret` are absent; they reach `Extension command does not support application context`. `Extensions.getAccessToken` exists only as an unwrapped global command, so it reaches the same rejection.

These are specific preview blockers, not claims that the legacy host lacks secret storage or authentication. A secret sample must first have an ownership-aware implementation and an isolation/cleanup acceptance scenario. An authentication-provider lifecycle sample can still be added independently of `getAccessToken`.

The same prerequisite's `ExtensionFileWatcher.ts:create` requires every root to start with `file://`, then explicitly throws `Disk watchers are unavailable for application filesystem providers` when an application is present. A disk-watcher extension cannot run in this static playground; a native sample needs a disk workspace and must await/dispose its watcher. This restriction does not exclude the separate `registerFileChangeHandler` API.

Additional source-backed boundaries inspected in the same worker prerequisite and the LVCE integration source:

- `WorkspaceProgressProviderRegistry.ts:notifyChange` invokes `WorkspaceProgress.handleChange`. The extension-management command is unwrapped and is neither shared nor handled by `invokeForApplication`; refresh rejects through its default branch. Registration suppresses that initial notification error, so successfully registering alone is not proof of visible progress.
- `WebRtc.ts` invokes `WebRtc.startWebRtcAudioStream`, `WebRtc.setRemoteDescription`, `WebRtc.stopWebRtcAudioStream`, and `WebRtc.readMicLevels`. These commands are unwrapped and absent from the application router's allowed cases. A static audio example requires an ownership-aware route before peer/permission cleanup can be tested.
- LVCE `packages/shared-process/src/parts/LanguageServerConnection/LanguageServerConnection.ts` imports `spawn` from `node:child_process`, resolves the server URI with `fileURLToPath`, and spawns that executable. `ExecuteLanguageServerCompletion.ts` uses `SharedProcess.invoke('LanguageServer.complete', ...)`. A browser worker server cannot simply be substituted into this published registration contract.
- LVCE renderer `ExtensionHostDebug.js` calls `ExtensionHostShared.executeProvider`; that helper invokes global `Extensions.executeProvidersByEvent` without the preview's application ID. An isolated preview provider is in the application registry, so it is not reachable through that discovery route.
- LVCE renderer `PortProvider.ts:forwardPort` and `stopForwardPort` explicitly reject any workspace URI outside `remote-ssh://`. Registering a synthetic provider could demonstrate a list, but would not demonstrate a working forwarded endpoint in the static playground.
