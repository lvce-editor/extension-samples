A sample demonstrates a user-facing capability; it does not need to repeat every type, registry snapshot, or low-level helper used to implement that capability.

The playground uses the tree-shakeable `@lvce-editor/api` package and its browser runtime. It does not use the legacy `extension-host-worker` facade as its sample import surface. The legacy facade contains host and registry plumbing beyond the author-facing browser package; those helpers are not separate sample requirements.

## Audited capability groups

The initial audit used the published API 9.46.0 exports; the reconciled examples use 9.47.0. Public `execute*`, registry snapshot/reset, and view-state functions are host integration helpers exercised by the corresponding provider/view examples. Types and low-level path/filesystem/cache variants do not each represent a separate user capability.

It is a different host facade from the tree-shakeable API bundled here; native process services need native fixtures rather than pretending to run in this static workspace.

## Validation status

The reconciled samples pass 65 unit tests using published server/shared-process/static-server 0.123.11 and editor-worker 19.74.3. Type-check, lint, formatting and Knip also pass. The served renderer and editor bundles were checked against the installed npm artifacts.

Published browser coverage includes preference cancellation/update/reset with source isolation and row geometry, document symbols after unsaved edits, reference result navigation, signature documentation, brace completion and undo, closing tags, comments, selection expansion, and tab completion, local authentication lifecycle, cache cleanup, watcher disposal, and preview tab navigation. Save/rebuild/reset, failed-build recovery, reload and generated output are exercised by the full suite. Formatting scenarios wait for the actual editor selection before typing, and all nine targeted repetitions pass. The sample PR must pass its full Chromium suite and Ubuntu, macOS and Windows quality jobs before merging.

## Verified application-runtime restrictions

Inspected extension-management-worker source at merged prerequisite `7704caeb775f706f5822a1355137a648a4eec677` (published 4.90.2):

- `GetOrCreateIsolatedExtensionHostWorker.ts` creates an application-scoped callback for the playground's isolated extension. Its non-specialized calls route through `Extensions.invokeForApplication`.
- `CreateExtensionCommandMap.ts` deliberately forwards application callbacks to that router instead of using legacy secret callbacks.
- `CommandMap.ts`'s `invokeForApplication` only accepts state-wrapped commands, an explicit set of shared theme commands, and its switch cases. `Extensions.getSecret`, `Extensions.storeSecret`, and `Extensions.deleteSecret` are absent; they reach `Extension command does not support application context`. `Extensions.getAccessToken` exists only as an unwrapped global command, so it reaches the same rejection.

These are specific preview blockers, not claims that the legacy host lacks secret storage or authentication. A secret sample must first have an ownership-aware implementation and an isolation/cleanup acceptance scenario. The Authentication Provider sample demonstrates its local session lifecycle independently of `getAccessToken`.

The same prerequisite's `ExtensionFileWatcher.ts:create` requires every root to start with `file://`, then explicitly throws `Disk watchers are unavailable for application filesystem providers` when an application is present. A disk-watcher extension cannot run in this static playground; a native sample needs a disk workspace and must await/dispose its watcher. This restriction does not exclude the separate `registerFileChangeHandler` API.

Additional source-backed boundaries inspected in the same worker prerequisite and the LVCE integration source:

- `WorkspaceProgressProviderRegistry.ts:notifyChange` invokes `WorkspaceProgress.handleChange`. The extension-management command is unwrapped and is neither shared nor handled by `invokeForApplication`; refresh rejects through its default branch. Registration suppresses that initial notification error, so successfully registering alone is not proof of visible progress.
- `WebRtc.ts` invokes `WebRtc.startWebRtcAudioStream`, `WebRtc.setRemoteDescription`, `WebRtc.stopWebRtcAudioStream`, and `WebRtc.readMicLevels`. These commands are unwrapped and absent from the application router's allowed cases. A static audio example requires an ownership-aware route before peer/permission cleanup can be tested.
- LVCE `packages/shared-process/src/parts/LanguageServerConnection/LanguageServerConnection.ts` imports `spawn` from `node:child_process`, resolves the server URI with `fileURLToPath`, and spawns that executable. `ExecuteLanguageServerCompletion.ts` uses `SharedProcess.invoke('LanguageServer.complete', ...)`. A browser worker server cannot simply be substituted into this published registration contract.
- LVCE renderer `ExtensionHostDebug.js` calls `ExtensionHostShared.executeProvider`; that helper invokes global `Extensions.executeProvidersByEvent` without the preview's application ID. An isolated preview provider is in the application registry, so it is not reachable through that discovery route.
- LVCE renderer `PortProvider.ts:forwardPort` and `stopForwardPort` explicitly reject any workspace URI outside `remote-ssh://`. Registering a synthetic provider could demonstrate a list, but would not demonstrate a working forwarded endpoint in the static playground.

Additional preview boundary evidence:

- Published API 9.47.0 `Preferences.openSettings` executes `Preferences.openSettingsUi`; `setSettingsSearchValue` targets `Settings.handleInput`. `Host.setWorkspaceUri` and `getRecentlyOpenedWorkspaceUris` target `Workspace.setUri` and `RecentlyOpened.getRecentlyOpened`. The hosted `Application.execute` router maps workspace reads and preference get/update explicitly, while other calls reach `ViewletManager.executeForApplication`, which requires an owned view instance. Preferences, Workspace and RecentlyOpened are services, not application view instances. These wrappers therefore need explicit host routing before a runnable preview can use them.
- API `markdownToVirtualDom` calls `Markdown.renderMarkdown` and `Markdown.getVirtualDom`; the same application router has no Markdown service route. `preparePrettyError` catches a missing host formatter and returns the serialized error, so its Output example can work independently.
- Extension-management 4.90.2 `ExtensionApplicationServices.createWorker` owns child workers by application generation, and `GetOrCreateIsolatedExtensionHostWorker` also supplies the owning extension ID. This supports `createRpc`; it does not supply the example's worker program. The playground's [compiler](../packages/playground/src/CompilerWorker.ts) emits one editable main bundle, and the [static builder](../packages/build/src/build.ts) builds `src/main.ts` per sample. A direct child-worker example needs an additional endpoint/build/lifecycle fixture. `createNodeRpc` additionally needs a Node connection; application RPC declarations explicitly accept only web-worker types.
